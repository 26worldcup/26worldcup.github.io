# 历史评分快照：让 "Simulate from X" 使用 X 时点的评分

日期：2026-07-20

## 问题

Forecast 页的 "Simulate from opener / date / match" 会重新模拟指定切点之后的所有比赛，但它使用的是**当前**的 `sim-model.json`，也就是已经吃进了整届世界杯结果的评分。结果是"从揭幕战重新模拟"这个动作带着后见之明：它知道英格兰这届踢得好（Elo +118），再拿这个认知去重演小组赛。

用户期望的语义是历史预测回放："模型在 X 那一刻是怎么想的"。

## 目标不变式

```
今天跑「from match N」  ==  在 N 开球前一刻跑「now」
```

两边使用同一套引擎代码，区别只在喂进模型的数据截止到哪里。这是本设计唯一的正确性标准。

模拟结果依赖五样东西，逐一对齐：

| 依赖项 | 当前是否满足 | 本设计如何满足 |
|---|---|---|
| 保留真实结果的比赛集合 | 满足 | `keepReal` 已按开球时刻切，不改 |
| FIFA 积分 `f` | 满足 | 本就冻结在 2026-06-11，全程不变 |
| 队伍 Elo `r` | 不满足 | 按切点快照 |
| 校准曲线 `curve` | 不满足 | 按切点快照 |
| 联盟偏移 `offsets` | 不满足 | 按切点快照（折进 `r`） |

## 为什么 curve 和 offsets 必须一起截断

初版设计打算只快照队伍评分，沿用全史的 `curve` 和 `offsets`，理由是世界杯 104 场对几十年校准样本的影响可以忽略。**实测证明这个判断是错的。**

`scripts/elo.mjs:238` 有一个世界杯情境收缩：曲线会向"仅世界杯决赛圈"的证据 `wcBins` 大幅收缩，`PRIOR` 只有 30。历史上世界杯决赛圈比赛总共才一千多场，塞进 104 场 WC2026 是很大的相对增量。

对比 `replay(全史)` 和 `replay(截到 2026-06-10)`：

- `curve` 各 bin 最大偏移 3.2 个百分点
- `offsets` 最大偏移 7.5 个评分点（CAF 38.0 → 45.5）

传导到夺冠概率上（同为赛前评分，20000 次模拟）：

| | ESP | ARG | FRA | ENG |
|---|---|---|---|---|
| 完全截断 | 20.45% | 17.13% | 13.76% | 8.40% |
| 只截断评分 | 21.06% | 17.49% | 14.39% | 8.78% |
| 差值 | +0.61 | +0.36 | +0.63 | +0.38 |

偏差本身不大，但是**系统性的**：所有强队一致偏高，跑多少次都不会消失。而"完全截断"那一行与 2026-06-11 git 中真实提交的模型（ESP 20.36% / ARG 16.76%）在噪声范围内吻合，验证了重建路径正确。

## 切点粒度：每场比赛

上游 CSV（`martj42/international_results`）只有 `date` 列没有开球时刻，同一天最多 8 场比赛无法区分。但**我们自己的 `matches.json` 有每场的精确开球时刻**，所以不受这个限制。

关键在于：开球时刻用来**排序和选择**哪些比赛进入某个切点，而不是写进合成 CSV。切点 `n` 的定义是"按开球时刻排序后的前 `n` 场"，粒度由集合成员决定，与 CSV 只有日期无关。

切点数 = 1 个赛前基线 + `matches.json` 中**已有比分**的场次数。全部踢完时是 105 个。

注意 FIFA 数据源会滞后于 CSV：截至 2026-07-20，决赛 `#104` 在 `matches.json` 里仍是 `scheduled` 无比分，而 CSV 已经收录了 2026-07-19 的结果。本设计以 `matches.json` 为准（它才有开球时刻），所以最后一个切点会在 FIFA 源补上决赛比分后才出现。这不影响正确性：`modelAt` 对超出最后一个切点的 cutoff 返回最后一个切点，本就是应有行为。

## 实现方式：合成 CSV + 每个切点独跑一次 replay

不改 `scripts/elo.mjs` 的任何逻辑。做法是为每个切点合成一份 CSV 文本，交给现有的 `replay()`：

```
preWc      = CSV 过滤掉 date >= '2026-06-11' 的行
wcRows[i]  = 第 i 场世界杯比赛序列化成的 CSV 行（按开球时刻升序）

cuts[n] = replay(preWc + wcRows[0..n-1])
```

`n = 0` 就是纯 `preWc`，即赛前基线。这样 `curve`、`offsets`、`ratings` 三者天然都截断在同一时点，无需把 `replay()` 内部的 `bins` / `wcBins` / `cross` 外露续接，也就没有续接出错的可能。

序列化 WC 比赛为 CSV 行时（列为 `date,home_team,away_team,home_score,away_score,tournament,city,country,neutral`）：

- `tournament` 写 `FIFA World Cup`，`replay()` 的 `kFor()` 自然给出 K = 60
- `home_team` / `away_team` 用 `DATASET_NAME[code]`，与 CSV 的队名空间一致
- `home_score` / `away_score` 用 `home.score` / `away.score`（120 分钟比分）。点球决胜因此按平局计入，`pen` 字段不参与，与 CSV 的约定一致
- `neutral` 仅当东道主在本国场地时写 `FALSE`（实测 13 场，按 `venues[venueId].country` 判定），其余写 `TRUE`。`HOME_ADV = 100` 由 `replay()` 自行施加
- `neutral=FALSE` 把 `HOME_ADV` 给的是 `home_team` 列那一方，所以东道主当客队时必须连同比分一起换进该列（实测 3 场：`#51` CAN、`#53` MEX、`#59` USA）。换整个 side 对象即可，比分随之而动；`neutral` 要在换完之后再算

**关于同日排序**：`scripts/elo.mjs:188` 的比较器 `(a, b) => (a.date < b.date ? -1 : 1)` 对相等日期恒返回 1，是个不自洽的比较器，同日多场的排序由引擎实现决定。这对本设计**无害**，因为世界杯任何一队一天不会踢两场，同日各场更新的是互不相交的队伍对，`dr` 也都基于当日开赛前的评分，与顺序无关。切点 `n` 的结果只取决于**哪 n 场被包含**，不取决于它们在 CSV 里的先后。这一点值得在实现时写进注释，避免日后有人误以为顺序重要。

**成本**：一次完整 `replay()` 是 106 ms，105 次约 11 秒。管线每 15 分钟运行一次，可接受；且赛事已结束，这份文件基本写一次就固定。选择这个"笨但显然正确"的实现，是因为它把正确性归约到了已经在生产中跑了一个多月的 `replay()` 上。

## 数据契约

新文件 `public/data/sim-model-history.json`，由 `scripts/update.mjs` 与 `sim-model.json` 同时产出。

```jsonc
{
  "cuts": [
    {
      "n": 0,                           // 已折入的世界杯比赛场数
      "after": null,                    // n=0 为 null；否则是第 n 场的开球时刻
      "curve": [{ "w": 0.4362, "d": 0.2908 }, ...],
      "teams": { "ARG": 2217, "ESP": 2247, ... }   // offsets 已折入
    },
    {
      "n": 1,
      "after": "2026-06-11T19:00:00Z",
      "curve": [...],
      "teams": {...}
    },
    ...
  ],
  "hostBonus": 60,
  "f": { "ARG": 1877, "ESP": 1875, ... }           // FIFA 积分全程共用一份
}
```

`cuts[n]` 的语义是"按开球顺序折入前 n 场世界杯比赛之后的模型"。`after` 记录第 n 场的开球时刻，`cuts` 按 `n` 升序，`after` **单调不减**。

不是严格递增：小组赛末轮同组两场必须同时开球以防默契球，共 12 处并列时刻（如 `#51` 与 `#52` 同为 `2026-06-24T19:00:00Z`）。并列时该组中间的切点无法被任何 `cutoffMs` 命中，`modelAt` 会返回两场之前的那个切点，而 `keepReal` 同样把两场都排除。两边一致，不变式不受影响。

`f` 提到顶层不重复存储，因为它冻结在 2026-06-11 全程不变。`hostBonus` 同理是常量 60。

体积估算：105 × (48 队 × 11 字节 + 13 段曲线 × 24 字节 + 元数据) ≈ 90 KB 未压缩，gzip 后约 10 KB。

`SimModel` 类型不变。客户端从某个 cut 重建 `SimModel` 的方式是把 `teams[code]` 和顶层 `f[code]` 组装成 `{ r, f }`。

## 加载

`src/data/DataContext.tsx` 加一个 `loadSimHistory()`，与现有 `loadSimModel` / `loadWcHistory` 同一个懒加载模式：`simHistoryRequested` ref 去重、失败时重置 ref 允许后续重试。

`sim-model.json` 保持原样不动。"最新"路径零改动、零额外请求，只有用户真去动时间选择器时才拉历史文件。

## 切点查找

在 `src/sim/` 新增一个纯函数模块（建议 `src/sim/history.ts`），只导出一个函数：

```
modelAt(history, cutoffMs: number): SimModel
  -> 取满足 (after == null || Date.parse(after) < cutoffMs) 的最大 n 对应的 cut，
     组装成 { curve, hostBonus, teams: { [code]: { r, f } } }
```

**所有模式共用这一个查找**，各自只负责算出 `cutoffMs`：

| 模式 | cutoffMs |
|---|---|
| `opener` | `-Infinity`（落到 `cuts[0]`，赛前基线） |
| `match` | 该场的 `Date.parse(m.date)` |
| `date` | `new Date(cutDate + 'T00:00:00').getTime()` |
| `now` | 不调用，直接用 `sim-model.json` |

这三个 `cutoffMs` 与 `Forecast.tsx:93` 的 `keepReal` 谓词使用的是**同一个值**，判据也同为"严格早于 cutoff"。因此 `keepReal` 为真的比赛集合，恰好等于已折进快照评分的比赛集合。不变式由此成立，而不是靠两处逻辑各自小心对齐。

`now` 模式不查历史文件，因此不触发额外加载。

## 页面改动

**Forecast**（`src/pages/Forecast.tsx`）：`simMode` 已有 opener/date/match/now 四态，改动是把传给 `runTournament` 的 model 从固定的 `simModel` 换成 `modelAt(...)` 的结果。历史文件未加载完成时，非 now 模式的模拟按钮置为等待态。

**MatchSimulator**（`src/pages/MatchSimulator.tsx`）：新增一个日期 `<select>`，选项为"最新"、"开赛前"、以及 35 个比赛日，默认"最新"。选中某个比赛日时，`cutoffMs` 用**该日当地 00:00**，与 Forecast 的 `date` 模式完全一致，也就是"该日开赛前的评分"。选项列表从 `matches.json` 现算，不存进历史文件。

选"该日开赛前"而非"当日收盘"，一是与 Forecast 共用同一条查找规则不引入第二种语义，二是这才是用户真正想问的：选 2026-07-19 得到的是**决赛开踢前**模型对西班牙和阿根廷的看法。

两页各加一行说明文字，显示当前使用的评分截止时刻。新增 i18n key 需覆盖全部 23 种语言。

## 验收

初版设计打算用 `probs.json` 的全部 104 场做 1.0pp 容差的回归，实测证明这个容差站不住，原因不是重建有误而是上游摄入滞后远大于预估。分层如下。

**第一层 a，精确验收：同期 CSV 配同期产出。** 把 `a46faa2` 时的 CSV 喂给 `buildHistory`，其 `cuts[0]` 必须与同一提交的 `sim-model.json` 全部 48 队**逐字相等**，零容差。两端都钉死在 git 里，测的是算术（过滤边界、offsets 折入、取整）能否复现管线自己的产出。实测 48/48 一致。

**第一层 b，今天的基线只做粗筛：25 分。** 不能要求今天的 `cuts[0]` 等于 06-11 快照。上游不仅补录世界杯结果，也**回溯补录和修订赛前比赛**：赛前部分的行数从 49400 涨到 49416，还有整行被改（2009 年 Island Games 的 `country` 列从 `Sweden` 改成 `Finland`）。今天重算赛前基线有 5 队与当日快照不同：ALG +12、ENG +5、POR +3、AUT +1、GER +1。ALG 的来源是上游补录的一场 `2026-06-10,Bolivia,Algeria,0,4` 友谊赛。

**这些补录是真实发生在世界杯之前的比赛，计入它们更正确而非更错误。** 要求今天的基线等于旧快照，等于要求数据保持陈旧，与"用今天的模型只喂到 X 为止的数据"这一前提相悖。

**第二层，早期比赛日：0.5pp。** 6 月 11 日至 13 日共 6 场，实测偏差 0.02 到 0.11pp。此时管线尚无滞后可累积，任何 `csvRow` 的主客对调错误、点球比分取用错误或曲线截断错误都会在这里暴露。

**第三层，全赛程粗筛：8pp。** 仅用于拦截量级错误，不作为精度保证。

**为什么全赛程不能收紧。** 上游 `martj42/international_results` 摄入世界杯结果有数天滞后，`probs.json` 冻结时用的是滞后的评分，而我们的重建假设截止时刻之前的比赛全部已计入。实测按比赛日的最大偏差：

| 区间 | 最大偏差 |
|---|---|
| 06-11 至 06-24 | 1.01pp |
| 06-25 至 07-07 | 6.65pp |
| 07-09 至 07-18 | 3.86pp |

偏差随赛程单调放大而非随机散布，且最早的 8 场是 0.02 到 0.16pp，这个形状只能由滞后累积解释，不可能由重建逻辑错误产生（逻辑错会从第一场就错）。

从 git 历史也能直接看到滞后：`sim-model.json` 中 USA 的评分走的是 1817（06-11）→ 1864（06-16）→ 1905（06-20）→ 1822（07-19），开赛后数日才开始反映小组赛结果。

**只对已完赛的比赛断言。** 未开球的比赛在 `probs.json` 里存的是当前模型现算的值而非冻结值（决赛 `#104` 目前就是这种情况）。测试需按 `status === 'finished'` 过滤。

实现顺序上，第一层和第二层要**先于**其余改动跑通，确认重建路径正确后再往下做。

**不变式测试。** 对若干个 N，断言 `from match N` 使用的 model 与"喂到 N 开球前"重建的 model 逐字段相等。用固定种子的 `rnd` 让 `runTournament` 确定化，断言两条路径产出同一个 `SimRun`。

**回归测试。** `now` 模式的输出不得改变；`sim-model.json` 的内容不得改变。

**冒烟。** `scripts/smoke.mjs` 加一条：`sim-model-history.json` 存在、`cuts.length === 1 + matches.json 中有比分的场次数`、每个 cut 的 `teams` 覆盖全部 48 队、`cuts[0].after === null`、其余 `after` 单调不减。

## 不做的事

- 不改 `sim-model.json` 的格式或内容
- 不改 `probs.json` 的生成逻辑
- 不改 Matches 页的夺冠赔率条（它是 `now` 语义，本就该用最新评分）
- 不为历史切点重算 FIFA 积分（2026-06-11 那期是整届赛事的官方排名，冻结是正确的）
- 不做增量编码压缩（10 KB gzip 不值得引入折叠逻辑）
